# 连接方式、助手发现与加密核查

2026-10-18，当前开发版本 1.0.1-dev.2，接续 dev.1 演示。使用者要求服务器中转、局域网、P2P 三种方式，拒绝 Cloudflare Tunnel；随后明确允许 CDN 前置保护 Oulu IP，并要求不改其他业务。本页区分当前实现、已确认的问题和目标方案；旧截图和旧验收只描述当时版本。

## 连接方向与本轮变更

| 方式 | 当前代码 | 交付边界 |
|---|---|---|
| 自建 Relay | 电脑主动出站连接，手机配对到服务器，转发 WebSocket 与已认证 HTTP 文件请求 | Oulu 新节点已部署并通过公网协议验证。可配置一个节点，两节点自动切换及身份同步尚未实现 |
| 局域网直连 | 手机连接电脑 Agent，默认 7420；电脑本地配对页签发独立设备凭据 | 已有完整业务链；目前是 ws/http 明文。Relay 配对凭据与局域网配对凭据独立，现有备用 URL 列表不能保证跨方式无感认证 |
| P2P 打洞 | 尚无 ICE/STUN/DataChannel 代码 | 必须新建真正的数据通道；改地址顺序、端口探测、Tailscale 地址可达都不能冒充内置 P2P |
| Cloudflare 隧道 | 已从当前开发源码移除自动启动、配对入口、桌面状态及部署服务模板 | 旧 --tunnel 参数明确报错；不再隐式启动 cloudflared。其他业务已有的 cloudflared 服务保持原状 |

桌面与启动脚本统一启用已配置的 Relay，TERMDESK_RELAY=0 仍可禁用。没有中转配置时局域网可独立工作。当前 /status.json 返回真实中转配置/连接状态，并明确 P2P 尚不支持，不返回伪造的成功状态。

## 部署前的服务器只读核查

资料来源为使用者提供的服务器目录，并通过已有 SSH 别名做只读状态检查。没有在仓库复制 SSH 密钥、代理分享链接、API 密钥或真实节点凭据。

| 节点 | 实际观察 | 下一步 |
|---|---|---|
| RackNerd | Node 已有；termdesk-relay 活跃，7421 仅监听回环；cloudflared 活跃，未见公网 TLS 监听 | 现有公网入口仍有隧道依赖。需要新增独立的 TLS 入口，并测试实际使用网络可达性，不能只删除电脑端依赖就称迁移完成 |
| Oulu | 未找到 node；termdesk-relay 未运行；nginx 与 cloudflared 活跃；443 已有服务，80/8443 也在监听 | 资料中的“未装 nginx”等条目已过时。新增服务前核对现有路由、TLS 证书和端口，保留共享代理服务 |

初始准备了独立 9443 入口方案；使用者随后选择 CDN 前置与现有 8443 端口。进一步核查发现旧业务域名其实是 DNS 直连，为避免改变该记录，新建了 TermDesk 专用的代理子域名、证书与独立站点。没有改旧域名的 DNS、证书、业务路由，也没有新增公网监听端口。

新增 Relay 仅监听 127.0.0.1:7421，使用独立非登录用户、独立 Node 22.23.3、256 MB 内存与 20% CPU 配额。公网经 CDN → Nginx 新站点 → 回环 Relay；TermDesk 路径仅接受已有可信 CDN 网段及回环来源。直连源站访问验证返回 403，公开地址验证返回 200。证书与续期使用独立目录和计时器，不接管原有证书任务。

旧业务 Nginx 配置、主配置与可信 IP 清单均比对 SHA-256 一致；Nginx/Xray/cloudflared 主进程 PID 未变，原首页与 /api/status 仍为 200。为加路径短暂添加到旧站点的引用已完整还原，最终只保留独立新站点配置。只执行过配置检查与平滑加载，没有重启既有业务服务。

本机默认 Relay 配置已改到 Oulu，旧配置私下备份；已运行的旧 Agent 需重新启动新版本才会读取。节点地址与凭据来自运行设备配置，不写进通用源码。已配对旧节点的手机需重新配对，当前没有无感跨节点迁移。

服务器中转不等于服务器运行 AI：它只转发到拥有工作目录和助手的 Agent。公网入口必须使用有效 TLS 证书与 wss/https；Relay 上保存节点/手机凭据哈希，客户端持有实际凭据。

## P2P 应怎样实现

建议采用 WebRTC DataChannel，复用自建节点作为认证后的信令与 STUN 服务。手机与电脑交换 ICE 候选并建立可靠有序通道；正文、审批、终端和文件数据都要有对应承载，不能只让少数帧走 P2P 就把整条连接标为直连。[WebRTC 官方连接说明](https://webrtc.org/getting-started/peer-connections)说明了候选交换和 STUN/TURN 的职责，[DataChannel 说明](https://webrtc.org/getting-started/data-channels)描述任意数据传输。

建议自动模式尝试局域网、P2P，失败后使用服务器中转，并提供手动选择与实际路径显示。该顺序是建议，尚未写成已生效的策略。TURN 或现有 WebSocket Relay 真正在转发业务时，界面必须显示“服务器中转”，不称“打洞成功”。

接入前要解决统一设备身份：同一绑定可以在各路径认证，节点失效后仍能认证，吊销在所有路径生效；节点恢复和网络切换不能重复发送排队消息。完整验收至少覆盖不同 NAT、双手机、断网重连、大文件及打洞失败回退。

## 传输加密的实际情况

| 路径 | 当前保护 | 没有的保护 |
|---|---|---|
| 局域网 ws/http | 设备令牌、可选额外访问密钥、服务端权限检查 | 没有 TLS；同网段被动监听风险不能靠 token 消除 |
| 公网 Relay wss/https | 手机到入口、电脑到入口分别由 TLS 保护；电脑的 Relay 连接拒绝公网 ws，回环测试例外。本轮实测客户端侧 TLS 1.3 / TLS_AES_256_GCM_SHA384 | TLS 在 CDN/中转入口终止，CDN 与 Relay 可读取正文；不是应用层端到端加密 |
| P2P | 尚未实现；选用 WebRTC 时由其 DTLS 数据通道保护链路 | 还没有可用的 P2P 会话、设备密钥绑定和实际直连证明 |

后续局域网加密可采用 TLS 加配对时确认的证书/设备身份；需要单独实现证书信任与更新，不能用“信任所有证书”。若要求中转也看不到正文，还需独立的端到端加密协议及设备密钥生命周期。本轮没有自造密码协议，也没有宣称 E2EE 已存在。

## DSH 到什么程度

已有 DSH 专用 SDK 适配：--profile sdk --patch，initialize 指定 provider/model/cwd；同一运行期连续 prompt，结果/工具/状态转换，关闭时结束独立 runtime。本轮修复移除了个人供应商与模型默认值，缺少明确路由会拒绝启动。

本机 PATH 有 dsh.cmd/ps1，但启动器指向已经不存在的旧 Roaming 目录入口；仅 --help/--version 就报 Harness CLI not found。这只能证明该启动器失效，不能推断整个 DSH 运行时不存在。

进一步只读检查实际桌面安装包的 app.asar，确认内嵌 @deepseek-ai/dsh、SDK app/server/protocol 和 llm-pi-ai，实际版本为 **0.2.1-rc.1**。桌面程序通过 Electron 的 Node 模式启动自己的 dsh-desktop-host；这与 TermDesk 目前使用独立 Node 启动 SDK CLI 的方式不同。TermDesk 尚无经过验证的 ASAR 内 SDK 调用路径，不能报告“本机 DSH 已完成验收”。

此前核查的 npm 0.2.1-rc.2 与本机实际 rc.1 都有 session/resume 的实现；TermDesk 尚未接入，故 resume:false。当前协议核查未发现单轮 cancel，TermDesk 通过结束该会话 runtime 停止。本机 rc.1 的模型 schema 允许省略 contextWindow/maxTokens/input，未知模型采用 SDK 默认能力假设；这不是对真实供应商能力的发现。

缺口包括：接入本机真实封装入口或支持独立 SDK 安装、按实际版本验证 overlay 加载/多轮、持久恢复的一致性与失败处理。不得以修启动器为名改动用户现有 DSH 安装或账号配置。真实模型回合还需单独许可，本轮未发任何模型提示。

## 动态发现与 ACP

ACP 是 Agent Client Protocol。项目已有通用适配器，负责会话、事件、权限、模型/模式及终端桥接；OpenCode、MiMo、Command Code 使用该路径，具体能力仍须各自握手并按版本验证。共享协议适配不是每个助手全功能验收。

此前发现只在固定品牌名单内找文件，部分 Windows 分支仍依赖旧安装目录。实际检查确认本机有 Claude Code 的 npm 命令入口，但旧注册表没有它；DSH 的残留启动器也不能表示可运行。当前工作是把入口定位共用化：显式覆盖、PATH、实际 npm prefix 与 bin 元数据、受限安装元数据及用户登记；不执行未知程序猜协议，不扫描整块硬盘。

正确的状态至少区分：检测到安装线索、入口完整、协议可用、模型/账号可用。未知 CLI 可以报告待接入，不能自动假定它支持 ACP。Claude Code 的 CLI 与 ACP 也不是同一接口；如使用 ACP 桥接器，还要明确桥接器是否实际安装。

动态发现现已共用 PATH 与 npm bin 元数据解析，支持移动安装目录、非默认 npm prefix、Node shebang 入口和显式登记。Claude Code 2.1.289 已检测为“安装存在、协议尚未接入、不可选择”；DSH 会说明启动器目标缺失。Codex 实际聊天启动使用同一份启动规格，保留 Node 前置参数，修复界面发现与执行位置可能不一致的问题。

ACP 握手失败会影响新建会话选择，换入口后可重试恢复；不再只写错误文案却继续显示可选。本轮对本机 MiMo、Command Code 只执行 initialize 握手：分别自报 OpenCode 0.1.9、Command Code 1.74.1，并返回各自能力；这些声明不等于已实际执行历史恢复或模型请求。OpenCode 本机入口未找到，Qoder 仍未完成当前真实回合验收。
