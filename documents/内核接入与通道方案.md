# TermDesk 通道与内核接入方案（含实测记录）

> 记录日期：2026-10-04
> 文档性质：**架构决策 + 实测证据**。凡标「实测」的条目，都是本轮在本机真实跑出来的，附命令与原始返回；

## 0. 一页结论

| 决策 | 内容 |
|---|---|
| **通道** | PC 端做统一的 **TermDesk PC**：内置 cloudflared、发现本机内核、起服务转发给手机。**不用 VPS 中转**，也不做 P2P |
| **内核协议** | 一律按 **ACP（Agent Client Protocol）** 接入；Codex 走官方 **app-server**（语义等价） |
| **会话模型** | 统一 `SessionRef = {nodeId, engine, nativeSessionId}`；**历史 = 对话**，新建与打开历史同一条路径 |
| **自研解析器** | 删除。会话列表/历史/恢复全部由内核自己的接口提供 |
| **本地内核** | 做成 **ACP 服务端**，与专业内核同一种暴露方式；前端壳零改动 |
| **CLI 形状的内核** | 走 **shim**，并且 shim 可以「描述文件化」（见 §8） |

## 1. 通道方案

### 1.1 原理澄清：Cloudflare Tunnel 不是 P2P

Cloudflare Tunnel 是**反向代理**：CF 边缘终结 TLS，再把请求灌进隧道送到源站。手机与电脑之间不存在直连，也打不了洞。

真正能 P2P 的只有两类，都不适用：

| 方式 | 结论 |
|---|---|
| WireGuard / Tailscale 直连 | 本校园网打洞失败，流量绕中继（PC→纽伦堡 144ms，手机→孟买 217ms）。已排除 |
| WebRTC DataChannel | 需要信令服务器 + STUN；NAT 不配合时照样落回 TURN 中继。复杂度换不到收益 |

### 1.2 两种拓扑对比（实测过的是 B）

| | **A（选定）** 隧道跑在电脑上 | B（原方案）隧道跑在 VPS 上 |
|---|---|---|
| 路径 | 手机→CF边缘→隧道→`127.0.0.1:7420` | 手机→CF→隧道→VPS relay←(反向WS)←电脑 |
| 载荷穿过 CF 次数 | **1 次** | **2 次**（两段都走 CF） |
| 电脑侧要跑的进程 | TermDesk PC（自带 cloudflared 子进程） | agent（+VPS 上的 relay） |
| 额外组件 | 无 | VPS relay 服务 + node key + 设备凭据体系 |
| DSH Web 兜底路由 | 顺带就有（同一份 ingress） | 需单独加，此前已丢（`dsh.wolfoxlabs.xyz` 返回 404） |
| 多台电脑共用一个入口 | 不支持 | 支持 |
| 手机不持有主令牌 | 支持（见 §2） | 支持 |

**结论：单机自用选 A。** B 剩下的唯一实质优势是「多机共用入口」，等真有需求再上；由于 §2 会把传输与身份解耦，A/B 之间切换只是改一个 URL。

### 1.3 目标形态

```
手机 ──443──> Cloudflare 边缘 ──隧道(电脑主动出站)──> TermDesk PC ──> 内核进程
                （cloudflared 由 TermDesk PC 自己拉起/收掉）
```

- TermDesk PC 负责：拉起 cloudflared 子进程、维护 ingress、发现本机内核、对手机提供统一协议。
- ingress 只暴露 agent 的 WebSocket（可选再加 DSH Web），其余一律 404。
- 隧道凭据与配置放 TermDesk PC 自己的配置目录，不散落在用户主目录。

## 2. 身份与配对方案

### 2.1 现状问题（逐条，均可指到代码）

| # | 问题 | 位置 |
|---|---|---|
| 1 | **两套凭据并存**：直连用主令牌、走 relay 用设备凭据，由 URL 决定哪套有效 → 配错即静默失败 | `pc-agent/src/server.js`（本地令牌校验）vs `relay/src/relay.js`（设备凭据） |
| 2 | **配对是隐形的**：要在 VPS 的 config.json 里手工塞 `codeHash`，30 分钟过期，无生成工具、无界面、不能轮换/撤销 | `.tmp/prepare-deploy.mjs`（一次性脚本） |
| 3 | **主令牌存在手机上**（= 对电脑的任意命令执行权），首帧明文 bearer 发送 | `android/.../data/DeviceCredentials.kt` |
| 4 | **「断开」会删掉绑定**；连接失败与凭据错误在 UI 上无法区分 → 体感「每次都要重输」 | `AppViewModel.disconnect()` 旧实现 |
| 5 | 手输地址，打错 = 静默失败；单客户端（第二台手机静默顶掉第一台，4409） | `ConnectionScreen.kt`、`relay.js` |

### 2.2 目标模型：身份与传输彻底解耦

```
node   = 电脑上的 TermDesk PC 实例  → nodeId + Ed25519 公钥（首次运行生成）
device = 手机                       → Android Keystore 内不可导出的 Ed25519 私钥
绑定   = 一次二维码扫描
```

- **二维码内容**：`{v, nodeId, urls[], nodePubKey, code, exp}`。TermDesk PC 打印二维码/PNG，手机扫码后把**设备公钥**+code 交给 node，node 登记。
- **之后所有认证都是挑战-签名**，手机不再保存任何共享密钥；主令牌永不离开电脑。
- **一个 node 可挂多个 URL**（局域网 / 隧道 / relay），共用同一身份 → **换传输不需要重新配对**。
- 设备管理：手机侧可列出已绑定 node、重连、改名、解除绑定（调 node 的 revoke）。

### 2.3 错误分类（UI 行为表）

| 错误 | UI 行为 |
|---|---|
| `unreachable` | 保留绑定，自动重连，提示"网络不可达" |
| `node_offline` | 保留绑定，显示"电脑内核离线"，上线自动恢复 |
| `credential_rejected` | **唯一允许弹配对界面的情况** |
| `device_revoked` | 明确提示已解绑，引导重新配对 |
| `busy` | 提示已有客户端在连，不静默顶掉 |

### 2.4 可复用：Codex 自带远程客户端配对

**实测**：Codex app-server 提供 `remoteControl/pairing/start`、`remoteControl/pairing/status`、`remoteControl/client/list`、`remoteControl/client/revoke`、`remoteControl/enable|disable|status/read`。
→ 若不想自己实现设备配对，可直接复用 Codex 这套；TermDesk 只做「node 级」配对，**内核登录态（codex login / DSH credentials）永远留在电脑**。

## 3. 三个概念的区别：列表 / 回放 / 恢复

这三个词很容易混，混了就会做出"点开历史是空对话框"的产品。**本轮实测**：

| 概念 | 对应方法 | 返回什么 | 实测证据 |
|---|---|---|---|
| **列表** | `session/list` / `thread/list` | **只有目录信息**：`sessionId / cwd / title / updatedAt` | 实测 opencode/mimo `session/list` 返回的第 1 条只有这四个字段，**一条消息正文都没有** |
| **回放**（历史正文） | `session/load` / Codex `thread/read` | 把历史消息交给客户端渲染；ACP 里以 `session/update` 通知流的形式重放 | 实测 opencode `session/load` 通过，期间收到 `session/update` 回放通知 |
| **恢复**（附着） | `session/resume` | **只把内核接回该会话**，之后发的消息延续原上下文；**不还历史正文** | DSH 的 `session/resume` 只返回 `{configOptions}`（源码 + README 一致） |

**类比**：`list` = 文件列表（文件名 + 时间）；`load` = 打开文件看到内容；`resume` = 把文件重新打开以便继续写。

**所以"能列出来"不等于"能看到内容"。** 打开一条历史会话时：
- 有回放 → 对话框里直接铺出原来的对话；
- 没有回放 → 对话框是空的，得等用户发第一条消息才看到新内容（体验不可接受）。

**内核给不了回放时的三条替代路**（按优先级）：

1. **读内核自己的持久日志**（DSH 路线）——用它的编解码模块，别手搓格式；
2. **TermDesk 侧缓存**——只对"经由 TermDesk 产生的对话"有效；**你自己在桌面 App 里产生的历史，缓存是空的**，所以这条单独用不了；
3. 退化成"只读标题"——不接受。

## 4. 会话统一方案

### 4.1 身份

```
SessionRef = { nodeId, engine, nativeSessionId }
```

- codex 的 `nativeSessionId` = thread id；DSH/OpenCode/MiMo = 内核自己的 session id。
- TermDesk 可以保留运行时句柄、UI id、request id，但**都必须映射到原生会话**，不能成为另一套上下文的权威。

### 4.2 一条路径

```
open(ref)  →  ref 有 id：resume / load
           →  ref 为空：new
           →  两者产出同一个 Conversation + Composer
```

- 「继续对话」按钮**消失**：打开历史会话时直接 attach/resume。
- 引擎若声明不能恢复（工作目录消失、或不支持），输入框禁用并给出明确原因。
- 发送按钮可用性由 `capabilities.canSend` + 节点状态 + 附着状态决定。

### 4.3 删除 / 保留清单

| 删除 | 保留 |
|---|---|
| `sessions.js` 的 Codex JSONL 与 DSH zstd 解析器 | 引擎发现（probe/版本/健康） |
| `chat.js` 里每轮 spawn `codex exec` 的逻辑 | adapter 注册表 |
| 自造 chat id 的逻辑 | 事件归一化（一套渲染） |
| `sessions.*` 与 `chat.*` 双对象 | 离线缓存（只作可用性保障，不作上下文来源） |

## 5. 内核接入契约

### 5.1 ACP 最小面

| 能力 | 级别 | 说明 |
|---|---|---|
| `initialize` + 能力声明 | 必须 | 决定 UI 如何降级 |
| `session/new` | 必须 | 新建 |
| `session/list` | 必须 | 列历史（分页） |
| `session/prompt` + `session/update` | 必须 | 发送 + 流式回传 |
| `session/cancel` / `session/close` | 必须 | 取消 / 释放 |
| `session/resume` | 强烈建议 | 真正的继续对话 |
| `session/set_config_option` | 加分 | 切模型 / 推理强度 |
| `session/load` | 可选 | 历史回放（有它则连历史读取都交给内核） |
| `request_permission` | 可选 | 需要审批的内核 |
| `session/fork` | 可选 | 分支会话 |

### 5.2 capability 驱动的 UI

前端壳只读能力声明：`loadSession` / `sessionCapabilities{list,resume,fork,close}` / `promptCapabilities{image,embeddedContext}`。
缺什么就禁用什么，并在界面上说明原因——**不允许伪恢复**（把历史文本重新喂给新会话冒充续聊）。

## 6. 本轮实测记录

**环境**：Windows 11，codex-cli 0.158.0-alpha.2.1，DSH 0.2.0-rc.2，OpenCode 1.3.16，mimo(@mimo-ai/cli) 0.1.9。
**方法**：临时脚本（`E:\aiPic\termdesk\.tmp\acp-probe.mjs`、`.tmp\codex-probe2.mjs`）以 stdio 拉起各内核，做 `initialize` 握手 + 列会话。均为只读操作（DSH 的 acp profile 是本轮新建，见 §6.4）。

### 6.1 四通道结果

| 通道 | initialize | 列表 | 新建 | 恢复/附着 | **历史回放** | fork |
|---|---|---|---|---|---|---|
| **codex app-server** | 通过（无需登录） | ✅ `thread/list` | ✅ `thread/start` | ✅ `thread/resume` | ✅ `thread/read` 直接返回结构化 thread | ✅ `thread/fork` |
| **DSH `--profile acp`** | 通过 | ✅ `session/list`（**读到桌面端同一个会话库**） | ✅ | ✅ `session/resume` | ❌ 无 `loadSession` | ❌ |
| **opencode acp** | 通过 | ✅ `session/list` | ✅ `session/new` | ✅ | ✅ **实测通过**（load 期间收到 `session/update` 回放） | 声明支持 |
| **mimo acp (0.1.9)** | 通过 | ✅ `session/list` | ❌ `session/new` → -32603 | ❌ | ❌ 声明 `loadSession:true`，**调用报 -32603** | 未验 |

### 6.2 关键结论

1. **四个内核都能列会话**——「手机上看到电脑上有哪些会话」这件事，四个通道全部通了。
2. **⚠️ 最重要的教训：能力声明 ≠ 真能用。**
   OpenCode 与 MiMo 都声明 `loadSession: true` + `sessionCapabilities {list, resume, fork}`，
   但实测 **MiMo 0.1.9 的 `session/new` 和 `session/load` 全部返回 `-32603 Internal error`**，而 **OpenCode（1.3.16）实测通过**（`session/new` 返回 sessionId + 模型选项；`session/load` 返回 `{sessionId, models}` 并回放 `session/update`）。
   → **落地前每个方法必须真调一次，不能按 README 或 capability 设计。**
3. **DSH 的 ACP 共享桌面端的持久化库**——`session/list` 返回的正是 `~/.dsh/sessions` 里那批真实会话（含 `E:\aiPic\termdesk` 的会话）。**"手机上看到的就是电脑上的历史"这条对 DSH 的列表部分直接成立**；但 DSH 没有回放能力，正文要另读（§12）。
4. **Codex app-server 无需登录即可列表**，`thread/list` 返回 `id / title / cwd / updatedAt / status / preview`，`thread/read` 返回 `{thread}` ——**Codex 的"回放"是直接给结构化 thread，比 ACP 的回放流更好用。**
5. DSH 的 `promptCapabilities` 全为 false（`image/audio/embeddedContext`），OpenCode/MiMo 为 true（含图片）——**UI 需要按能力裁剪**。
6. **列表 ≠ 正文**：`session/list` 实测只返回 `sessionId / cwd / title / updatedAt`，没有消息正文。要看内容必须靠回放或另读日志（详见 §3）。

## 8. CLI shim 的规范化（回答"能通用规范化吗"）

**能，但要分两层看：能描述化的做成 manifest，描述不了的才写解析器。**

### 8.1 adapter manifest（描述文件）

```yaml
id: qoder
kind: cli-shim
binary: "%LOCALAPPDATA%\\Programs\\QoderWork CN\\resources\\bin\\qoderclicn.exe"
capabilities: { list: true, resume: true, fork: true, cancel: false, stream: "ndjson" }
workspace: { args: ["-w", "{cwd}"] }
list:   { args: ["--list-sessions"], parse: "table" }        # 或 parse: "json"
new:    { args: ["--session-id", "{uuid}", "-p"] }
resume: { args: ["-r", "{sessionId}", "-p"] }
send:   { args: ["-p", "--output-format", "json", "{text}"], stream: "ndjson" }
map:                                                          # 事件映射表
  assistant_message: message
  tool_call:         tool
  tool_result:       tool_result
  turn_end:          turn
```

### 8.2 边界

| 情况 | 处理 |
|---|---|
| 有 `--list-sessions` 或 JSON 输出 | 纯 manifest，零代码 |
| 输出是 NDJSON 事件流 | manifest + 通用 NDJSON 解析器（仓库内置一个） |
| 只有人类可读文本 | manifest + 一个小解析器（adapter 私有） |
| 完全不流式（只吐最终结果） | manifest 里 `stream: none`，UI 诚实标注"非流式" |

**关键：shim 也是 adapter，不是第二条路径。** 手机端永远只有一条路径、一个会话列表、一个会话视图。

### 8.3 由此得到的扩展成本

- 说 ACP 的内核：**加一个 `kernels/<name>/`（多数只是配置）**，手机端零改动。
- CLI 形状的内核：**加一个 manifest**。
- 私有协议（如 Antigravity）：才需要真正的逆向工作，优先级最低。

## 9. 本地内核：做成 ACP 服务端

本地内核（Termux 沙盒）**不要发明私有接口**，直接实现 ACP 服务端（stdio JSON-RPC）：

- 对外只暴露 §5.1 那套方法，内部工具/权限/沙盒策略自己管；
- 在 TermDesk 里的身份：`{ nodeId: "local", engine: "termux", nativeSessionId }`，与远程内核同构；
- 好处：手机端零改动；本地/远程切换 = 换一个 adapter 实例；不产生任何"参数通道"这类私货。

**落地建议**：先只实现 `initialize / session/new / session/list / session/prompt / session/update / session/cancel / session/close / session/resume`，`loadSession` 可后补。

## 10. 分层与目录目标（消除黑盒）

```
android/                  纯壳：一个会话列表 + 一个会话视图（不碰内核私有格式）
pc-agent/src/
  server.js               与手机的协议、连接
```

| 项 | 说明 |

### 13.3 本轮新查明的内核事实（写代码必须知道的）

| 事实 | 证据 |

### 14.1 术语定死：产品上只有两个内核

与《本地内核方案》一致，并写进设置界面：

- **远程内核**（这台电脑）：会话、文件、终端、进程全部指向电脑。

之前把 engine 列表当“内核列表”展示，导致“为什么切换内核不可用”看不出答案；现在设置里先给“远程 / 本机”两个目标，再在远程下列引擎。

### 14.2 设置 → 内核与目标

- 列出电脑真实探测到的引擎（tier 与理由直接来自 PC 探针，不自己编）：已接入 / ACP·适配器未接入 / CLI·需要 shim / 未安装。

### 14.3 手机回退（真机验证）

以前按系统返回直接退到桌面。现在按层次逐级向上，只有全部关闭后才交给系统退出：

`新建对话 sheet → 打开的文件 → 侧滑面板 → 非会话页返回会话列表 → 会话抽屉 → 只读历史 → 正在聊的对话 → 退出`

实现方式：每个拥有临时界面状态的组件各自注册 `BackHandler`，子组件因组合顺序靠后而优先。真机已验：设置→会话、sheet→会话、对话→列表，均不再直接退到桌面。
