# 会话连续性与 Agent 配置架构方案（2026-10-11）

> 历史材料，保留原规划与当日状态；不代表当前完成度。当前实现、能力边界和目标结构见[架构设计](架构设计.md)、[功能清单](功能清单.md)及[本轮验收](演示版验收-2026-10-17.md)。原文游标增量方案已被本轮按需全量快照方案取代。

## 当前判断

TermDesk 已具备“同一 PC Agent 进程内继续对话”的基础能力，Codex 与部分 ACP 内核还可以通过原生 session/thread 恢复历史会话。当前还不能把它称为所有内核、所有重启场景都无缝：DSH 的 registry 仍声明 `resume: false`，PC Agent 重启后不能把磁盘记录自动变成可继续的 live chat；多设备场景也缺少完整的 session lease、事件游标补发和冲突状态。

Agent 配置同样是“部分可用”。Codex 已有 provider、model、reasoning effort、context window 等配置路径，ACP 可以发现模型和 session mode；最大输出、完整输入/输出模态编辑、新 provider 或任意新模型的手机端接入还没有完整写入链路。manifest 中标记为 `planned` 的字段只是诚实的能力路线声明，不代表当前按钮已经能生效。

## 目标结构

### PC Agent

保留 `kernels/registry.js` 作为发现层，新增 `kernels/manifest.js` 作为能力与配置契约层。每个内核向客户端提供同一形状的 manifest，声明：

- session：list、read、resume、fork、nativeTranscript
- turn：cancel、queue、liveTerminals
- model：source、dynamic、switch、add
- config：scope、liveApply、requiresRestart、schema

下一阶段把 `ChatManager` 拆成三层：

```text
chat/
  conversation-manager.js   生命周期、创建、关闭、resume/fork
  kernel-adapters/           Codex、DSH、ACP、CLI shim
  event-router.js            事件序号、重放、订阅、断线补发
  approval-broker.js         权限请求与超时
sessions/
  registry.js                磁盘 session 与 live chat 的统一索引
  continuity.js              lease、cursor、冲突状态
config/
  schema.js                  统一配置字段与作用域
  providers.js               provider/model registry
```

`handlers.js` 最终只负责协议路由和参数校验；业务动作下沉到上述模块，避免大 switch 同时承担协议、内核判断和状态修改。

### Android

按用户功能而不是技术对象拆分：

```text
core/connection/             WebSocket、重连、请求和事件游标
core/protocol/               frame 编解码与版本兼容
feature/chat/                消息流、发送、队列、审批
feature/session/             历史、恢复、分组、fork
feature/config/              manifest、模型、配置编辑
feature/files/               文件浏览、上传、下载
feature/terminal/            终端与进程
```

`AgentClient` 只保留连接状态和 StateFlow 聚合；帧解析继续放在 `AgentFrames`，各 feature 通过 repository 读取领域模型。这样可以让配置页只依赖 `KernelManifest`，不会再从 UI 代码猜某个内核是否支持某个按钮。

## 会话无缝衔接的落地顺序

1. 让每个 live chat 都有稳定的 conversation registry 记录，记录 kernel、native session id、runtime owner、最后 event cursor。
2. 断线重连时先发送 `chat.sync(chatId, afterSeq)`；PC 返回可补发事件、游标范围和是否需要完整快照。
3. 引入 session lease 与设备 owner。单设备续租，多设备显示“只读/等待接管/冲突”，避免两部手机同时写同一个 turn。
4. 对 DSH 选择一种明确产品策略：实现可持久化 resume，或在 UI 中始终标为“历史可读、重启后不可继续”。
5. 对 Codex/ACP 的 native resume 做端到端回归，覆盖 PC Agent 重启、Android 断网、重复提交和事件重复到达。

## Agent 配置的落地顺序

1. 统一字段 schema 和作用域：`next-turn`、`session`、`profile`、`runtime-restart`。
2. provider/model registry 支持发现、启用、禁用、默认值和来源；手机端只能编辑 manifest 声明为 `supported` 的字段。
3. 将 max output 接入 Codex、ACP 和 DSH 各自的请求参数，并为不支持的内核返回可读原因。
4. 将 input/output modalities 拆成“模型能力发现”和“本次请求选择”两层，避免把模型声明能力误当成可编辑设置。
5. 增加 provider/model 的导入与校验流程，再考虑手机端新增自定义模型；在此之前不提供看似可用但实际被忽略的输入框。

## 这次切片的边界
