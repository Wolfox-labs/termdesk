## 三、业务流程

### A. 配对与连接

```
电脑 /pair（pair.js）─ 配对码 / 二维码 ─→ 手机
   ├ 经中继：手机拿一次性码 → 中继换成"手机自己的凭据"
   │        → Computers.kt（电脑列表）+ DeviceCredentials.kt（Keystore 加密）
   └ 直连：给本机令牌；回退地址随 more= 一起下发
            （回退路径的鉴权尚未实现，方案见 后续任务.md）
手机 AgentClient 建 WS → 首帧 auth（带协议版本）→ version.js 比对 → auth.ok / auth.fail
服务端：routedSocket = 本连接（"最后一个认证的客户端赢"）
        → chats.attach + notifier.attach 建立单向推送路由
```

### B. 会话列表：内核 → 工作区 → 会话

```
手机 kernels.list ─→ kernels 帧（tier / 是否可用 / 能否续聊 / 真实原因）
手机 sessions.list ─→ handlers.js 汇总三路来源：
     Codex   内核自己的 thread/list + rollout 目录只用来发现 id（kernels/codex.js）
     ACP 系  各内核自己的 session/list（kernels/acp.js）
     DSH     磁盘直读（sessions.js；session.v4.jsonl.zstd 与旧名都认）
     ↓ 每条附 resumeVerdict()：由能力真值表决定 canResume 与"为什么不能"
手机 sessions.read ─→ session 帧（正文）
     → SessionGroups.kt 分组 / 排序 / 内核筛选（纯函数）
     → ChatIndexGroups.kt 绘制（工作区可收起，三级结构）
```

### C. 一轮对话（发送 → 流式 → 结束）

```
chat.send{chatId,text,requestId}
  └ ChatManager.send（chat.js）
      ├ 正在跑？→ 入队，并立刻推一条 queued:true 的用户行
      │            （手机显示"排队中 · 这一轮答完就发"）
      └ 否则 dispatchTurn → 按 contract.turnDriver 分派
            app-server→codex.js   acp→acp.js   sdk→dsh.js   cli→cli.js
内核回传：chat.event（转录项，记录在 item 字段）
          chat.status / chat.turn(ended|failed) / chat.approval / chat.terminals
回合结束（三处：finishCodexTurn / finishAcpTurn / DSH session.status=idle）
  → 清状态 + drainQueue（把排队的那条发出去）+ notify（产生通知）
手机侧：AgentFrames.kt 解析 → ChatTranscript.kt 绘制
        （用户 / 助手 / 思考 / 工具 / 命令行 / 注入上下文）
审批：chat.approval → 手机对话框 → chat.approve{requestId,optionId}
      → approvals.js 结算（绝不挂起：超时按 fallback；无客户端立即按 offline 结算）
取消：chat.cancel → 按 cancelStyle 分支 → stopTurn
      （同时清空队列并明说"队列中的 N 条消息未发送"）
```

### D. 接管（加入，而不是互斥）

```
chat.resume{engine,sessionId,path} → ChatManager.resume
   ├ 已有同一 engine+sessionId 的 chat → 返回同一个 chat
   │     + joined:true + 提示语（"双方看到的是同一个运行进程"）
   └ 否则 resumeAcp / resumeCodex
         Codex 另有内核级 active writer 拒绝：能读，不能接着写
提示语经 action.result 到手机 → snackbar
"文件 N 秒前被写过"这条证据必须在**接通内核之前**采样（thread/resume 自己会改写文件）
```

### E. 通知（PC 判定，手机只决定要不要打扰）

```
PC：回合结束 / 回合失败 / 审批待答 → ChatManager.notify → notify.js
   ├ 有客户端连着 → notify 帧直推
   └ 没人连着 → 保留并标 whileAway → 下次认证补发
                （投递即遗忘；上限 20 条 / 24 小时）
手机：Notifications.kt（IMPORTANCE_HIGH 渠道 + PendingIntent）
      → 点击 → MainActivity 意图 → 打开该会话
      → 若用户正在看那条会话则不再打扰；审批例外，内核还阻塞着
```

> 状态：PC 端有单测 18 项 + 线上 e2e 11 项；**手机端渲染尚未在真机验证成功**（见 `后续任务.md` B11）。

### F. 文件 / 终端 / 进程

```
fs.*    files.js     手机 FilesSection.kt（会话里的工作目录可一键跳进来）
term.*  terminal.js  手机 TerminalSection.kt（命令行会话可脱离对话独立存在）
procs/services  system.js → SystemPanel.kt
上传下载分片    transfer.js
```

### G. 本机沙盒（"本机"内核）

```
手机里跑同一个代理：LocalAgent.kt + LocalAgentService.kt + localkernel.js
"本机"内核 = 沙盒里的 DSH（打包的运行时 + 覆盖配置）
desktop/ = 只读展示壳（状态 / 内核表 / 二维码 / 日志）
```

## 四、如果再拆，落点排序

1. **`AgentClient.kt` 的帧分派**（**38** 个 `type` 分支，计数口径见第五节）→ 改成表驱动。
   这是唯一还在"每加一种帧都改同一个 `when`"的地方，也已经出过一次事故：
   两个同名 `"chat.sent"` 分支，后者（清除"发送中"）成了死代码，整个回合发送按钮转圈禁用。
2. **`handlers.js`**（954 行）→ 按域拆（会话 / 文件 / 终端 / 系统）。它是所有帧的入口，最容易继续长。
3. **`ChatSection.kt` 的输入区**（发送 / 停止 / 附件 / 待发提示）→ 独立文件；列表与转录早已拆出。

**门槛不是行数，而是那条边界**：新增一种帧类型，应当只改一处。行数会被功能吃掉，边界不会。

## 五、怎么重新测量（数字过期时用这个）

```powershell
# 三个宿主文件与拆出来的模块
$r='E:\aiPic\termdesk'
git -C $r diff --stat a27ce34 HEAD -- pc-agent/src/chat.js
git -C $r diff --stat 79a7a17 HEAD -- android/app/src/main/java/dev/termdesk/app/ui/ChatSection.kt
Get-ChildItem "$r\pc-agent\src\chat" -File | ForEach-Object { "{0,5} {1}" -f (Get-Content $_.FullName).Count, $_.Name }

# 宿主文件的增长来自哪些提交
git -C $r log --format='%h %s' --numstat a27ce34..HEAD -- pc-agent/src/chat.js

# 帧分派还有多少个分支（16 空格缩进 = 顶层 when 的分支。别用"带点帧名"的模式，会漏掉无点帧名）
(Select-String -Path "$r\android\app\src\main\java\dev\termdesk\app\data\AgentClient.kt" -Pattern '^ {16}"[a-zA-Z._]+" ->' | Measure-Object).Count
```

**关于口径（踩过一次）**：`(Get-Content $f).Count` 数的是**原始行数（含空行）**，而
`Get-Content $f | Measure-Object -Line` **不数空行**——同一时刻的 `chat.js` 分别是 2090 与 1961。
两个口径差着 100 多行，混用会得出互相矛盾的结论（本文件第一版就写错了）。**这份文档统一用原始行数**，
比较历史版本时用 `@(git show '<rev>:<path>').Count`，一次只用一种口径。

**第二次数错的是"统计模式"本身**：本文件第一版数帧分支用的是 `^\s+"[a-z]+\.[a-z.]+" ->`，
只匹配带点的帧名，`status` / `chat` / `notify` / `error` 等 **10 个无点帧名**全被漏掉，
于是得出 28（当时报 29，因为那会儿还多一个重复的 `chat.sent` 分支）。真实值是 **38**。
教训与上一条同源：**数字要能解释它为什么是这个值**——38 = 28 + 10 个漏掉的，这个等式当时就该被问一次。

**这份文档该在什么时候更新**：新增一个模块、新增一类帧、或做完上面第四节任何一条之后。数字与结构不符时，以命令输出为准，并顺手改掉这里。
