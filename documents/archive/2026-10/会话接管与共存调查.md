# 会话接管与共存调查（本轮第 2 项）

调查时间：2026-10-08，全部数字都是本机实测，命令可复现。**只读，没有发起任何真实模型调用。**

## 一、为什么要先调查

目标是"手机无缝接管电脑上正在跑的会话，电脑端再无缝回归"。能不能成立不取决于我们想不想，
取决于三件事同时成立：

| | 条件 | 为什么关键 |
|---|---|---|
| ① | 同一个会话的记录是**共享且追加**的 | 手机写进去的内容，电脑端再打开才看得见 |
| ② | **第二个客户端**能打开同一条会话 | 打不开就只能"看"，不能接手 |
| ③ | 两个客户端**同时写不会分叉** | 否则两边各自以为在对话，内容悄悄分成两份 |

硬约束：桌面端（Codex App、DSH 桌面版、OpenCode TUI）都是第三方应用，**我们改不了它**。
所以①②只能依赖内核自身性质，我们唯一能控制的是③里属于我们这一侧的部分。

## 二、结论

| 内核 | ① 共享记录 | ② 第二个客户端能打开 | ③ 同时写 |
|---|---|---|---|
| Codex | 成立：列表与内容都来自内核自己的接口，不是我们解析磁盘 | 成立：`thread/resume`（cod​ex.js:475） | **未知**：两个 app-server 进程各持内存状态却写同一个 rollout 文件，没有任何锁 |
| DeepSeek Harness | 部分成立：磁盘是共享的，但**我们读不到新格式**（见第四节） | **不成立**：registry.js:117-121 明确 `resume:false`，界面写"历史恢复尚未开放" | 未知；我们目前只读 |
| OpenCode / MiMo Code / Command Code（ACP） | 成立：列表来自内核自己的 `session/list`（acp.js:481-491） | 成立（能力探测通过时）：`session/load` 会在返回前把整段转录重放回来（acp.js:570-582） | 未知 |
| QoderWork（CLI shim） | 成立：CLI 自己的索引 | 取决于 `replay` 标记；本机 CLI 未登录，**未验证** | 未知 |

一句话：**"共存"不能承诺，"接管 + 交还"可以**。因为①让交还有了物质基础（记录在共享存储里），
②让接管成为可能，而③没人保证——所以必须由我们在界面上把"谁现在持有"讲清楚，而不是假装两边能同时写。

## 三、逐内核证据

### 3.1 Codex

- 会话**标识**从 rollout 目录的文件名发现，但**内容与元数据一律由内核返回**。理由已经写在
  `codex.js:239-253`：`thread/list` 只返回最近窗口（实测 54 条根会话里只给了 9 条），
  而 `thread/read` / `thread/resume` 对任何 id 都有效。因此手机看到的列表 = 内核自己的列表。
- 实测磁盘：`~/.codex/sessions` 下 142 个 `.jsonl`，**0 个锁文件**，最新一条 10-06 21:58。
- **内核级硬限制（读代码得到，非推断）**：另一个进程正在写该线程时，`thread/resume` 会被内核以
  `active writer` 拒绝，`chat.js` 把它翻译成"该会话正在电脑端被使用，手机上暂时无法接手"。
  也就是说 **Codex 桌面版持有某条线程时，手机接不过去**——这是内核的决定，不是我们的选择。
  能读（`thread/read` 回放），不能接着写。
- ③ 未验证。桌面版 Codex 与我们的 app-server 是两个进程（推断：我们 spawn 的是自己的子进程），
  两边都能 `thread/resume` 同一个 thread id，而 rollout 是追加式 JSONL，没有任何互斥。
- **另一个实测发现**：`thread/resume` 本身会**改写 rollout 的 mtime**。最初把"文件最近被写过"
  当作"别人正在用"的证据时，这一条让手机对着一条两天前的会话报"0 秒前被写过"——量到的是我们自己。
  所以这条证据必须在**接通内核之前**采样（现在如此，并有回归用例钉住）。

### 3.2 DeepSeek Harness

- 布局：`~/.dsh/sessions/--<目录名编码>--/<会话 id>/<会话文件>`
- 实测 268 个会话目录：**230 个只有 `session.jsonl.zstd`**、**23 个只有 `session.v4.jsonl.zstd`**、
  **15 个两份都有**。两份都有的 15 个里，**v4 全部更新（15/15，晚几小时到几天）**，且 v4 通常更小
  （例：plain 3286KB@10-04 → v4 2139KB@10-07），说明桌面版把日志迁移/重写成了 v4 并继续写 v4。
- 桌面版此刻正在写的那条（`--E-aiPic-通用沙盒基建--/21e0f1f4…`，19:01 本地时间）目录里**只有 v4 文件**。
- 恢复：`registry.js:117-121` 的 `resume:false` 是"权威而非占位"，注释写明假称可恢复会造出
  "按了必然失败的按钮"。所以 ② 今天不成立。

### 3.3 ACP 系（OpenCode / MiMo Code / Command Code）

- 列表：`session/list` 由内核回答（acp.js:481-491），没有能力就诚实地返回空列表。
- 打开：`session/load`（acp.js:575），它会在 resolve 之前把整段转录以 `session/update` 通知重放，
  所以调用方必须先把路由装好（注释里点了 `ChatManager.resumeAcp`）。
- `acp-probe.js` 另外记录了 ACP 的第二种原语 `session/resume`——"在新进程里继续一条已持久化的会话"。
  这和我们用的 `loadSession`（回放）**不是一回事**，对"接管"很可能更合适，但**尚未实验**。
- **实测（2026-10-08，队列 e2e）**：ACP 的 `chat.send` 是**回合结束时才应答**的——内核在回合末才 resolve
  `session/prompt`。两个后果：①手机端"发送中"的转圈会持续整轮；②若发送按钮以"发送中"为禁用条件，
  用户在 ACP 上就**无法在回合中发第二条**（DSH 上可以，它的回执提前返回）。这是需要与"排队"对齐的地方
  （见 `后续任务.md` B12）。

### 3.4 QoderWork（CLI shim）

- `loadSession` 直接绑定 `m.replay`（cli.js:164），真正的继续靠 CLI 自己的 `--resume`。
- 本机 CLI 未登录（启动横幅显示 `○ QoderWork CN`），所以 ① ② 都没有实测。

## 四、调查中发现的两个真缺陷

### 4.1 DSH 新格式的会话读不到（23 条，包含今天最新的）

- 位置：`sessions.js:400`（列表时写死 `session.jsonl.zstd`）、`sessions.js:441`（按 id 读取时同样写死）
- 影响：**静默**少 23 条会话。列表只是短了一截，没有任何提示；而这 23 条恰好是最近在用的。
- 依据：23 个目录只有 v4 文件名；两份都有的 15 个目录里 v4 全部更新。
- 修法：两处都接受 v4 名；两份都在时用 v4。**规则用证据定，不猜**：15/15 都是 v4 更新。

### 4.2 DSH 存在"第二套读取器"

- Codex 的教训已经写在 `sessions.js:423-430`：内核自己会服务会话，"第二个读取器只会与内核报告的内容漂移"。
  但 DSH 仍然由我们自己解析磁盘，于是内核一改格式（v4）我们就静默失效。
- 方向：优先走 DSH 自己的会话接口；磁盘解析降级为"接口不可用时的回退"，并在界面上标明来源。

## 五、仍然未知（必须靠实验，不猜）

1. **③ 并发写**：所有内核都没有锁。需要实验——桌面版打开某条会话时，我们从另一个进程
   `thread/resume` / `session/load` 同一条，两边各写一句，看转录是否交错、上下文是否分叉。
2. Codex 桌面版是否会察觉到"另有人持有同一条线程"。
3. ACP 的 `session/resume` 是否比 `loadSession` 更适合接管（继续而不是回放）。
4. DSH 是否提供可编程的会话打开接口（若有，② 就能成立，接管 DSH 才有意义）。

## 六、由此确定的实现约束（已按使用者的判断修订）

使用者的判断（2026-10-08）：**每个内核只接受一个终端设备的输入，不存在真正的并发；前端只是一个
展示壳，消息打进内核排队等待，而排队发生在 PC 端。所以不做互斥，做好无缝交接即可。**

于是第 4 项落在"把已经成立的事实说出来"，而不是加锁：

1. **同一条会话只有一个运行时**：`chat.js` 本来就保证这一点（`resume` 发现已有同一
   `engine + sessionId` 的 chat 时直接返回它）。所以接管在结构上早已成立，缺的是**可见性**。
2. 接手的回答带 `joined` 与一句话：加入别人的会话时说"双方看到的是同一个运行进程，发消息会进
   同一段对话"；文件在 120 秒内被写过时说"这台电脑上这条会话的文件 N 秒前被写过（可能是桌面端
   应用）"。**证据必须在接通内核之前采样**，否则量到的是自己（见 3.1 的实测发现）。
3. 措辞只说**测到了什么**（文件变过），不说**是谁写的**：mtime 无法归因。
4. 看不到证据就说看不到：ACP 系的内核存储在内核自己的接口后面，`lastWriteOf` 返回 null，
   此时**什么也不说**，而不是给一句让人安心的假话。
5. 能力门保持权威：`resume` 为假的内核（今天的 DSH）被拒绝，且**拒绝时不附加任何提示**——
   在被拒的动作下面写一句话，会被读成"其实做成了"。
6. Codex 的 `active writer` 拒绝保持原样：内核不允许两个写者，这不是我们该绕过的东西。
7. 排除一个看似合理的方向：**不做租约/互斥**。使用者已明确并发不存在、排队发生在 PC 端，
   加锁只会把"接管"变成"被拒绝"，而拒绝不是无缝。

## 七、验证状态

- 本文档第一至四节的数字均为 2026-10-08 本机实测（142 个 Codex rollout、268 个 DSH 会话目录、
  23/15/230 的分类、v4 15/15 更新、0 个锁文件）。
- **未验证**：第三节里标"未知"的并发写行为、DSH 的接口能力、ACP `session/resume` 的实际行为、
  QoderWork 的登录后行为。这些都需要真实内核实验，做之前会先问。
- 与本调查相关、同样**未验证**的两条，记在 `后续任务.md`：通知在真机上没有出现（B11）；
  以及"文件被写过"这条证据只在**接通内核之前**采样时才可信——顺序已有回归用例钉住，
  但**从未在桌面端真的正在写某条会话时看到过**（Codex 那一边会先被内核以 `active writer` 拒绝，
  所以这一条大概率只能在 ACP 系上验）。
