## 顺序建议（2026-10-08 更新）

**先说三条教训，它们决定了下面的顺序**：这一轮真正修掉的四个缺陷，有三个是"能跑但答案是错的"——
静默少 23 条会话、把自测自己当成别人在写、死代码让发送按钮整轮禁用。**"能跑"不构成证据**，
所以下面的顺序把"把已有的东西验证到位"排在"做新功能"前面。

1. **B11（通知定位）**：唯一一个"写了、PC 端测过、真机上没见过"的功能。加一行日志复现即可分辨，
   成本最低、不确定性最高，必须先清掉——否则后面每加一个通知通道都是在猜。
2. **B12（ACP 排队一行修）**：现在只有 DSH 能排队，ACP 系（OpenCode / MiMo / Command Code）在 UI 上够不着，
   属于"同一个功能一半可用"。一行。
3. **B14（CI 首跑前置）**：解挂 CI 之前必须让读 token 的 e2e 优雅跳过，并加上"重复分支即失败"的门——
   这次的死代码 bug 就是编译器警告没人看造成的。
4. **B2 后半（会话内列产出文件）**：你亲口提的痛点，且已有可靠数据源（DSH `deliverables/presented`）。
5. **B15（表驱动帧解析 + 防回涨门）**：宿主文件已回涨超过拆包前，越晚做越贵。
6. **B16（双模式一致性）**：需要真机断网/切网，安排在真机窗口期。
7. 之后才是 **B1（权限一次选到底）/ B3（输入区）/ B4（分栏）** 这些体验项：改动面小、做完截图即可验收。
8. **A3（`qoderclicn login`）** 随时可插：你登录一次，QoderWork 就能从"不可选"翻成可选。
9. **C1（DSH 改 ACP）** 需要一次真实模型复验窗口，且会连带 B12 的实现方式，等你给窗口期。

**验证纪律（本轮新增，后续沿用）**：每个改动完成时，必须在提交信息里分开写"已验证"与"未验证"，
并给出未验证项的具体理由（缺设备 / 要花额度 / 依赖第三方）。本轮四个缺陷有三个是真机跑出来的，
不是读代码看出来的——真机时间不是开销，是发现问题的唯一途径。
