# Oulu 中转接入验收 — 2026-10-18

> 目标：手机**不再依赖 adb**（USB 反向转发 / 无线调试）也能连上这台电脑，改由 oulucloud 上的 relay 作为唯一入口。
>
> 结论：**做到**。两台手机（OPPO PDEM30、Redmi 25102RKBEC）都已在删除 `adb reverse` 之后通过 `wss://termdesk-oulu.wolfoxlabs.xyz:8443/termdesk` 连上；同一台电脑同时在线的手机上限已从写死的 1 改为可配置，本项目设为 2。

## 1 部署了什么

| 项 | 值 |
|---|---|
| 服务器 | oulucloud `172.247.44.74`（`ssh oulucloud`，端口 23456） |
| 域名 | `termdesk-oulu.wolfoxlabs.xyz` → **灰云直连**（Cloudflare 只做 DNS，代理已关；见第 7 节） |
| 对外入口 | `wss://termdesk-oulu.wolfoxlabs.xyz:8443/termdesk` |
| TLS | nginx 1.26.3，`listen 8443 ssl`，Let's Encrypt 证书（TLS 1.2/1.3，HSTS） |
| 反代 | `/termdesk` → `127.0.0.1:7421`，只放行这两个 relay 路径，其余 404，按 IP 限流 20r/s（burst 40） |
| relay | `termdesk-relay.service`，`/opt/termdesk-relay/`，只听回环 |
| 数据 | `/var/lib/termdesk-relay/config.json`（`termdesk:termdesk` 0600） |
| 节点 | `termdesk-pc-309391514336`（这台电脑，`~/.termdesk/relay.json`） |

电脑端以 `TERMDESK_RELAY=1` 启动 agent，主动拨出到 relay；手机只认这一个地址。

## 2 代码改动

`relay/src/relay.js`：

1. **`maxClientsPerNode`（默认 1）** —— 原来写死"一台电脑只许一台手机在线"，第二台一律 `close(4409)`。现在由部署配置决定上限，默认行为不变。
2. **三行运维日志** —— `computer … connected` / `phone … online (n/max)` / `phone … offline`。手机说"连不上"时，先看这三行能区分"没到 relay"、"被上限拒绝"、"连上又掉了"。
3. 拒绝时也记录当前连接数，例如 `phone … refused: 2/2 already connected`。

`relay/test/relay.test.js` 增两项：默认拒绝第二台、配置为 2 时两台同时在线且拒绝第三台。全套 **15 项通过**。

## 4 真机上遇到的三个问题

1. **第二台被拒（4409）**：不是网络问题，是 relay 的写死上限。已改为配置项（见上）。
2. **`/pair` 静默退化成"局域网直连"**：每台电脑最多 5 个待用配对码，`/pair` 每访问一次就占一个、agent 启动也印一个；堆满之后不再报错，只是页面从"配对码"变成"配对令牌"、地址变成 `ws://<局域网IP>:7420`。清空 `config.json` 的 `pairings` 后恢复。
3. **手机进后台就断**：ColorOS/HyperOS 的省电策略会掐掉连接，App 自己也提示"系统可能不允许 TermDesk 在后台运行"。这不是 relay 的问题；两台手机之所以"轮流在线"，是因为另一台在后台被掐断了。要真正常驻，需要在系统里放行后台运行/关闭省电限制。

## 5 还没做

- 两台手机的系统后台放行（否则"同时在线"只在两端都前台时成立）。
- 桌面控制台"设备"页里 24 条历史记录大多是调试期留下的，需要按台清理（relay 侧另有 6 条测试设备记录）。
- 手机安装包仍只能走局域网或 adb（relay 只转发已配对手机的 `/download`、`/upload`）。
- 版本：本轮把 agent 版本推为 `1.0.1-dev.4`，桌面安装器随之重打；手机 APK 仍是 dev.3（未重装）。

## 6 真机反复断连的定位（当晚补充）

Redmi 在 21:00 前后每 30–40 秒掉一次线、自动重连，实测把原因从"relay 有问题"排到"手机到 Cloudflare 的这段路不可靠"：

| 测什么 | 结果 |
|---|---|
| relay 是否稳定 | 电脑侧保持 150 秒，双向 ping/pong 正常；relay 单测 15 项通过 |
| 电脑→relay | 一直在线，没有掉过 |
| 手机→relay（8443） | TLS 握手 0.7–7.6 秒，6 次请求里 2 次 10 秒超时；失败时连接被 relay 心跳判定为掉线（日志里带 `by heartbeat`） |
| 手机→Cloudflare 443（对照，www.cloudflare.com） | 0.6–0.8 秒，稳定 |
| 手机→百度 | 0.18 秒，正常 |
| 手机→源站直连（`--resolve` 到 172.247.44.74:8443） | 0.62–0.71 秒，三次全部有响应（被 nginx 的"仅限 Cloudflare 来源"规则挡住返回 403，但链路本身是好的） |

结论：**中转进程和电脑侧都没问题，是手机到 Cloudflare 这一段（本 zone 的 TLS 握手）慢且丢**。因此 WebSocket 会在几十秒内被卡死，表现为"连上又断开"。

过程中顺带修掉的两个 relay 问题（已部署）：

1. 同一台手机重连时，旧连接仍占着名额，一台手机能把 `maxClientsPerNode` 全占满、然后自己也被 4409 拒绝。现在同设备的旧连接由新连接**接管**。
2. 被接管的旧连接还会发帧，旧代码取不到记录会抛异常并把整个 relay 进程带崩（当晚 21:02 实际崩过一次）。现在丢弃该帧，并给帧处理加了 try/catch，一帧坏数据不会再拖垮中转。

修复后 15 项单测通过，relay 已在 oulu 上重启运行。

## 7 切成灰云直连（当天晚上已执行）

结论确认后直接改成了直连，不再经过 Cloudflare 代理：

| 做了什么 | 细节 |
|---|---|
| DNS | 用本机 `~/.cloudflared/cert.pem` 里带的 API token 调 Cloudflare API，把 `termdesk-oulu.wolfoxlabs.xyz` 的 A 记录改成 `proxied: false`（灰云），内容仍是 `172.247.44.74` |
| nginx | 去掉"仅限 Cloudflare 来源"的 403 门禁；改为只放行 `/termdesk` 与 `/termdesk/` 两个 relay 路径，其余一律 404；按来源 IP 限流 `20r/s`（burst 40）；加 HSTS；TLS 保持 1.2/1.3 |
| 证书 | 沿用原来的 Let's Encrypt 证书（**主机名没变**），所以手机端不需要重新配对 |
| 回滚 | 控制台把这条记录改回橙色云，并把 `/root/termdesk-relay-locations.conf.bak-20261018`、`/root/termdesk-relay-site.conf.bak-20261018` 放回原位后 `systemctl reload nginx` |

**安全边界**（源站 IP 现在公开，靠下面这些而不是靠"藏在 CDN 后面"）：

- 只暴露 8443 一个端口，且只有两个 relay 路径；80 端口只服务 ACME 验证。
- TLS 1.2/1.3 + HSTS，证书是 Let's Encrypt 正式证书。
- 建链要过 relay 的节点凭据（`nodeId` + 32 字节密钥，服务端只存 sha256）。
- 手机各自持有独立设备凭据，可单台吊销；配对码 12 位、一次性、10 分钟、每台电脑最多 5 个待用。
- 认证失败按来源 IP 限速（relay 自身 8 次/30 秒），nginx 再加一层 20r/s 的请求限流。

**实测**：直连路径 TLS 握手 0.36–0.93 秒、5 次全成功（此前经 CF 是 0.7–7.6 秒且 1/3 超时）；切换后电脑端节点连接保持稳定，没有再出现几十秒一次的 1006。

**一个坑要记住**：DNS 有缓存，切完的一段时间里不同解析器仍会返回旧的 Cloudflare 地址（本机 Windows 解析器就反复拿到旧答案，`Resolve-DnsName -DnsOnly` 却是新地址）。这时手机/电脑可能还连在 CF 上，看起来像"改了没用"。等 TTL 过期即可；本机没有管理员权限，所以没有改 hosts 强制定向。
